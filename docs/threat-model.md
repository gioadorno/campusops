# Threat Model

## Scope and assets

Protected assets are user identity, support-request confidentiality and integrity, authorization policy, JWT signing material, policy integrity, service state integrity, audit integrity, and gateway availability. MCP clients, models, arguments, prompt text, and HTTP input are untrusted. Phase 1 uses fictional data and local in-memory state.

| Threat                   | Attack                                                                              | Explicit mitigations                                                                                                                                                                    | Residual risk / next control                                                                                                                                                       |
| ------------------------ | ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Prompt injection         | Policy or support text tells a model to ignore instructions or invoke a write tool. | Prompts label embedded text untrusted; tool authorization is deterministic and independent of the LLM; writes need `requests:write`; identity cannot be supplied as an argument.        | A permitted user/model can still choose an undesirable authorized action. Add confirmation policy and host UX for sensitive actions.                                               |
| Tool poisoning           | Malicious names/descriptions or a compromised registry misrepresent a tool.         | Tool surface is statically registered in source; annotations match behavior; descriptions do not grant authority; the server checks scopes and ownership regardless of client metadata. | Protect build provenance and dependency integrity with locked CI, review, signing, and SBOM controls.                                                                              |
| Data exfiltration        | A caller requests broad records or coerces output of secrets.                       | Per-user support queries; ownership checks; bounded limits; fictional data; no general query/eval/filesystem/network tools; audit excludes content; tokens are never tool results.      | Add response classification, rate limits, anomaly alerts, and egress policy before real data.                                                                                      |
| Excessive permissions    | A broad token enables unnecessary writes or audit access.                           | Small allow-listed scopes; separate read/write scopes; every handler checks its requirement; no implicit admin bypass.                                                                  | Use short-lived audience-bound tokens, consent/step-up, role mapping, and periodic entitlement review.                                                                             |
| Malicious tool arguments | Oversized, malformed, or crafted strings trigger unsafe behavior.                   | Strict Zod schemas, trim/min/max constraints, enum allow lists, integer bounds, and no dynamic code, shell, path, URL, or SQL execution.                                                | Add request byte limits and rate limiting at production ingress.                                                                                                                   |
| Secret exposure          | JWT secret or bearer token appears in source, errors, or audit.                     | Runtime environment configuration; minimum secret length; audit schema cannot accept arguments or tokens; error payloads omit credentials; `.env` ignored.                              | The local default is public and development-only. Production requires managed secrets, rotation, redaction, and log scanning.                                                      |
| Replay / retry           | Network retries duplicate a support request or repeat cancellation.                 | Create requires a non-empty bounded idempotency key indexed with user ID; duplicate creates return the original record and `created: false`; signed tokens expire.                      | In-memory keys disappear on restart. Production needs durable atomic idempotency records, retention, token replay defenses where appropriate, and a defined cancel retry contract. |
| Cross-user data access   | A caller supplies or guesses another user's request ID.                             | No `userId` input exists; principal derives from verified JWT; list filters by principal; get and cancel independently check record ownership; tests cover violations.                  | IDs remain observable if leaked. Production should use opaque identifiers, monitoring, and consistent error policy to reduce enumeration signals.                                  |

## Trust decisions

Authentication answers who the caller is. Authorization answers whether that principal may attempt an operation. Ownership answers whether that particular record is accessible. These are separate checks. The LLM participates in none of them.

## Availability and local limitations

Schema limits constrain individual payloads, but Phase 1 has no HTTP rate limiter, concurrency budget, durable queue, or circuit breaker. The in-memory repositories and audit sink are neither durable nor horizontally consistent. These are accepted local-demo limitations, not production guarantees.
